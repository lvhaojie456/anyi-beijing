# 小红书产品工程师面试项目讲法

本文按“产品工程师”面试准备：既要讲清用户问题和产品判断，也要讲清工程落地、取舍和下一步迭代。

## 项目定位

一句话：

安忆是一个面向纪念、追思和情感陪伴场景的 Android 产品，从移动端体验、云端账号体系、UGC 社区、AI 陪伴、内容审核、合规页面、运维后台到腾讯云部署材料做了一个可演示的端到端闭环。

面试时不要把它讲成单纯 Android Demo。更合适的定位是：

- 我从一个垂直情感场景出发，拆成纪念馆、AI 陪伴、社区互助和运营后台四条主线。
- 我自己完成了客户端、后端、数据模型、上传链路、后台审核、官网和部署文档。
- 这个项目能体现“发现需求、定义 MVP、快速全栈实现、再基于风险补齐合规和运营能力”的产品工程能力。

## 2 分钟项目介绍

可以直接这样说：

我做的项目叫安忆，是一个面向纪念和情感陪伴场景的 Android 产品。这个场景的核心痛点不是单纯记录信息，而是用户在低频但强情绪的时刻，需要一个安静、可信、可持续的纪念空间。所以我把产品拆成四个部分：云端纪念馆、AI 陪伴、人文社区和运营后台。

技术上，客户端用 Kotlin + Jetpack Compose，后端用 Node.js + Hono，数据库是 SQLite，并配了迁移、文件上传、限流、CORS、审计日志和管理后台。移动端可以注册登录、创建纪念馆、献花点烛上香、上传头像和素材、与 AI 陪伴聊天，也可以在社区发布图文、点赞评论、申请义工。后端提供账号、纪念馆、社区、AI、素材、审核、崩溃日志和账号注销接口。

我最想体现的是产品工程师能力：不是只把需求写成 PRD 或只写一个页面，而是从用户场景出发，把 MVP、交互、服务端、数据模型、风控合规、后台运营和部署链路都跑通。这个项目还有一些我会主动承认的不足，比如 Android 端目前集中在一个 Activity 里，远程礼祭和支付还只是数据模型和规划，没有完整接口闭环。下一步我会优先做模块化、指标埋点、真实内容安全服务和支付闭环。

## 8 分钟演示路线

1. 登录注册：展示账号体系、微信登录预留、token 会话、本地 session。
2. 纪念馆：展示纪念馆页面、献花、点蜡烛、上香、供品限制和云端状态同步。
3. AI 陪伴：展示微信式人物列表、头像上传或生成、人物记忆、聊天、AI 回复边界和免责声明。
4. 社区：展示图文发布、图片上传、点赞评论、义工招募和申请流程。
5. 个人设置：展示头像、昵称、协议、客服、账号注销入口。
6. 管理后台：展示上传审核、审计日志、崩溃日志、账号注销、文件删除队列。
7. 部署材料：展示 README、腾讯云部署文档、上线清单和官网。

演示时只讲真实完成的能力。支付、远程礼祭订单、商城可以说“数据模型和产品规划已预留，但我不会把未完成能力包装成已上线功能”。

## 最值得讲的技术点

- 客户端体验：Jetpack Compose 做了多页面状态、沉浸背景、底部导航、图片选择、上传、动态社区流和复杂纪念馆视觉状态。
- 网络层：`AnyiApiClient` 统一封装 API、Bearer token、多 baseUrl、JSON 和 multipart 上传。
- 后端 API：Hono 提供账号、纪念馆、社区、AI、素材、后台、法务页面和注销请求接口。
- 数据模型：SQLite migration 管理用户、纪念馆、社区、AI、素材、审核、审计、崩溃、账号注销等表。
- 内容与安全：上传审核、文本初筛、文件删除队列、审计日志、限流、CORS、路径穿越保护。
- AI 设计：服务端保存 API key；AI 陪伴提示词明确“不声称自己是逝者”；GPT 与 Gemini 图片接口分开适配并使用模型白名单。
- 运维闭环：崩溃上报、后台查看、部署脚本、Nginx/systemd 示例、官网和下载页。

## 必须主动承认的不足

- Android 端代码集中：`MainActivity.kt` 超过 6000 行，适合快速原型，但不适合长期多人协作。下一步要拆成 feature、ViewModel、Repository、Design System。
- 支付和订单闭环未完成：迁移里有订单和商城表，但当前 API 路由没有完整订单/支付接口。面试时不要说“已完成支付系统”。
- SQLite 是 MVP 选择：低成本、易部署，但规模化后要迁到 MySQL/PostgreSQL，并补充备份、索引、慢查询、连接池和读写隔离。
- 测试不足：目前主要做构建和类型检查，缺少 API 单测、端到端测试、Compose UI 测试和 CI。
- 数据指标还不完整：需要补埋点体系，例如注册转化、纪念馆创建率、社区发布率、AI 首聊率、7 日留存、上传审核时长。

## 高频追问口径

为什么做这个项目？

我想做一个情绪价值很强、但又需要产品克制的垂直场景。纪念类产品不是越热闹越好，核心是可信、安静、长期保存和低打扰。我选择这个题目，是因为它能同时考验产品判断、内容治理、AI 边界、合规和端到端工程能力。

这个项目和小红书有什么关系？

不是业务形态完全一样，而是能力模型相似：小红书是内容社区、UGC、互动关系、内容治理、AI 和商业化的综合体。我的项目里有图文社区、点赞评论、上传审核、AI 陪伴和后台运营，可以作为缩小版场景说明我理解“产品价值要通过工程系统落地”。

如果让你接入小红书式推荐流，你怎么做？

先做可解释的轻量排序：时间衰减、点赞评论、作者活跃度、图片数量、审核状态和用户互动历史。数据量起来后再做召回/粗排/精排，并关注冷启动、低质内容过滤、负反馈和多样性。现阶段不会一上来堆复杂模型。

AI 陪伴的伦理风险怎么控制？

第一，产品文案明确它是模拟陪伴，不代表真实逝者。第二，系统提示词限制 AI 不冒充逝者、不输出医疗法律等专业建议。第三，敏感素材必须走上传审核。第四，给用户删除人物、记忆和注销账号的入口。第五，后续要补内容安全模型和人工复核。

为什么不用 Firebase、Supabase 或更完整的云服务？

我想证明自己能掌控后端和数据链路，所以选择 Node + Hono + SQLite 快速搭建可部署服务。这个选择适合 MVP 和小规模测试，但我清楚规模化后要迁到托管数据库、对象存储、监控告警和 CI/CD。

如果重构，第一步做什么？

先不重写功能，先划边界：`feature-auth`、`feature-hall`、`feature-ai`、`feature-community`、`feature-profile`、`core-network`、`core-ui`。然后把 API 调用下沉到 Repository，把页面状态放进 ViewModel，最后补单测和 Compose UI 测试。

如果接口变慢，你怎么排查？

先看客户端超时、错误码和崩溃日志，再看后端访问日志、慢接口、SQLite 查询、上传文件大小、AI provider 延迟。对 AI 和上传接口单独设置超时、重试、降级和队列；对高频接口补索引和缓存。

## 面试前 24 小时清单

- 用手机或模拟器录一个 90 秒演示视频，避免现场网络不稳定。
- 准备一个普通账号和一个管理员账号。
- 确认 APK 可安装，后端健康检查可访问。
- 不要现场才注册微信登录，微信开放平台配置不完整时直接说是预留能力。
- README 已把远程礼祭/商城收紧为“预留数据模型与上线规划”，面试时也保持这个口径。
- 准备一页架构图：Android App -> Hono API -> SQLite / uploads -> Admin Web / Legal Pages。
- 准备一个“我会怎么改”的路线图：模块化、测试、埋点、推荐、内容安全、支付。
